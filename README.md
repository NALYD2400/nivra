# Nivra

Application Windows pour suivre ses comptes et les quotas disponibles. Elle utilise React, Vite et Tauri 2.

## Installation

Télécharger l’installateur Windows depuis les releases GitHub et l’exécuter. Nivra vérifie ensuite les nouvelles versions au lancement et régulièrement pendant son utilisation. La mise à jour peut aussi être recherchée dans **Réglages → Mises à jour** ; son installation est déclenchée par l’utilisateur.

Les mises à jour Tauri sont signées et vérifiées avant installation. L’installateur n’est pas signé avec un certificat de signature Windows ; Windows peut afficher un avertissement SmartScreen.

## Développement

La connexion Google Antigravity nécessite `NIVRA_ANTIGRAVITY_CLIENT_ID` et `NIVRA_ANTIGRAVITY_CLIENT_SECRET` lors de la compilation. Configure-les dans l’environnement de construction ou dans `.private/antigravity-client.env` à la racine du projet (une affectation `NOM=valeur` par ligne). Ce fichier est exclu de Git. En CI, utilise les secrets du dépôt. Sans cette configuration, les autres fonctions restent disponibles et Nivra indique que cette compilation ne permet pas la connexion Antigravity. Ces identifiants de client desktop sont embarqués dans le binaire ; ils ne remplacent pas les jetons personnels des comptes, conservés dans le coffre Windows.

Installer Node.js, Rust et les prérequis Windows de Tauri, puis lancer `npm ci` et `npm run tauri -- dev`. Pour un installateur, configurer `TAURI_SIGNING_PRIVATE_KEY` et `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, puis lancer `npm run tauri -- build`.

## Comptes et limites

- **Codex** : plusieurs comptes peuvent être connectés avec des profils séparés. Les quotas fournis par Codex sont actualisés périodiquement.

- **Claude Code** : une connexion via un profil séparé est proposée ; l’affichage des quotas n’est pas encore disponible.
- **Cursor** : Nivra peut ouvrir un profil Cursor distinct. Les quotas ne sont pas encore disponibles.
- **Antigravity** : Nivra peut détecter une adresse enregistrée sur cet appareil et lire les quotas des sessions locales ouvertes, en les associant à un profil uniquement si l'adresse renvoyée correspond sans ambiguïté. Lorsque la session locale fournit des fenêtres de cinq heures ou hebdomadaires, Nivra les affiche séparément des valeurs par modèle. Cette lecture a été testée sur des réponses simulées. Un parcours expérimental ouvre des profils séparés pour ajouter des comptes ; il doit encore être validé avec une installation et des comptes Antigravity réels. La page Antigravity peut demander au CLI installé sa liste de modèles et ouvrir une session interactive avec le modèle et le dossier choisis. Cette session utilise le compte du CLI, pas nécessairement un profil suivi dans Nivra. Une entrée dans la liste ne garantit pas l'accès effectif ; le lancement interactif depuis Nivra reste à vérifier.

Pour chaque profil Codex enregistré, **Modèles proposés par Codex** lit à la demande le catalogue de son app-server. Celui-ci peut être local ou mis en cache : la présence d’un modèle ne confirme pas que le compte peut effectivement l’utiliser. Cette lecture ne transfère pas la connexion Codex vers la passerelle Nivra.

Dans **Passerelle → OpenAI API**, **Continuer avec ChatGPT** propose une connexion séparée pour autoriser Nivra à utiliser un abonnement ChatGPT éligible. Active ensuite le compte enregistré. La passerelle utilise le catalogue de ce compte et accepte les requêtes Responses avec `stream: true` et `store: false`. Les requêtes Chat et Messages courantes en texte, avec images utilisateur et fonctions simples, sont traduites vers Responses ; les réponses Chat sans outils sont diffusées progressivement. Les requêtes avec outils et les flux Messages attendent encore la réponse complète. L’accès aux images dépend du modèle et du compte. Le comptage séparé de tokens et plusieurs options avancées ne sont pas encore pris en charge pour ce fournisseur. Oublier tente de révoquer l’accès puis retire la copie locale ; si la révocation ne peut pas être confirmée, vérifie les applications connectées dans ChatGPT. Un test local utilise un compte factice pour vérifier le routage Responses et la séparation des clés ; le parcours complet, les modèles et l’utilisation de l’abonnement n’ont pas encore été vérifiés avec un compte réel. Cette connexion est distincte des profils Codex existants.

Le bouton **Connecter le compte du CLI** ouvre le parcours de connexion Google interactif du CLI installé (`agy acp --login`). Il concerne la session du CLI, distincte des profils Antigravity de Nivra. Termine la connexion dans la fenêtre ouverte, puis recharge les modèles. Ce parcours n'a pas encore été vérifié jusqu'au bout avec un compte réel.

Le bouton expérimental **Ajouter un compte Google** prépare séparément un compte pour la passerelle : il ouvre Google, vérifie l'identité et cherche le projet Cloud Code Assist avant de conserver le jeton de renouvellement dans le coffre Windows. **Vérifier** renouvelle l'accès, vérifie l'identité et le projet, puis affiche les modèles et les fenêtres de quota que Google renvoie pour ce compte. Les fenêtres absentes restent inconnues. Si Google renvoie une valeur de disponibilité ou de quota pour un modèle, elle est affichée séparément ; elle ne prouve pas nécessairement le quota global. Il utilise les identifiants publics du client Antigravity et une interface Google non officielle, susceptibles de changer. La connexion complète, le renouvellement, les modèles et les quotas restent à vérifier avec un compte réel. **Retirer** supprime le jeton local ; l'autorisation Google se gère depuis le compte Google.

Après vérification d'un compte, **Essayer un modèle** envoie une seule demande texte à Google avec ce compte et le modèle sélectionné. Cet essai utilise le quota de ce compte ; il n'est pas relié à la passerelle et ne prend pas en charge les outils ni les conversations. Le protocole a été testé avec un serveur simulé, pas avec un compte réel.

Un compte Antigravity enregistré peut démarrer directement la passerelle ou être ajouté à une passerelle déjà active. Ce routage expérimental accepte une requête `/v1/chat/completions` avec une conversation texte alternant utilisateur et assistant et d’éventuelles instructions initiales, ou `/v1/responses` et `/v1/messages` avec une conversation texte équivalente. En Chat, Responses et Messages, les appels de fonctions simples et leurs résultats sont pris en charge expérimentalement : Nivra conserve en mémoire les fragments signés nécessaires au retour de l’outil pendant 30 minutes maximum, dans une limite de 64 tours et 4 Mio. Avec des outils, Nivra attend la réponse complète de Google avant de produire les événements SSE ; les options avancées restent indisponibles. Pour Messages, Google doit fournir les nombres de tokens utilisés, sinon une erreur est renvoyée. La limite de sortie demandée est transmise à Google si elle est comprise entre 1 et 65 536 tokens ; elle vaut 2 048 par défaut et reste soumise à la limite du modèle. La température, top-p et les séquences d’arrêt sont transmises quand elles sont fournies et prises en charge par le format client ; leur disponibilité dépend du modèle. Si la limite est atteinte, Nivra renvoie le texte disponible en indiquant que la réponse est incomplète. Pour Chat et Responses sans outils, un flux SSE est transmis progressivement depuis Google. Pour Messages, Nivra attend encore la réponse complète avant de l'envoyer en SSE. Un échange texte et un appel d’outil ont été effectués avec le client Codex installé et un fournisseur Antigravity simulé. Le lancement Codex est accessible à titre expérimental ; le parcours avec un compte réel et l’ouverture interactive restent à vérifier. Un échange texte et un aller-retour de lecture de fichier ont également réussi avec Claude Code en profil isolé et un modèle Gemini 3 simulé. Ses niveaux de raisonnement low, medium et high sont traduits approximativement vers Gemini 3 ; les autres modèles ou niveaux sont refusés. Les indications de cache Messages sont acceptées sans créer de cache Google. Le lancement Claude Code est disponible à titre expérimental ; les autres outils et le parcours avec un compte réel restent à vérifier. Les trois formats acceptent aussi les images PNG, JPEG, WebP et GIF intégrées en base64 (8 Mio maximum de données encodées par image), y compris dans les conversations avec des outils. Les URL d’images externes ne sont pas prises en charge. La prise en charge des images est testée avec des requêtes simulées, pas avec un compte réel. Le compte et le modèle sont vérifiés avant chaque requête, qui utilise le quota du compte. Des tests HTTP vérifient le routage, l'authentification locale et les formats SSE avec des réponses simulées ; l'authentification Google et la génération sont testées séparément avec des services simulés. Le parcours avec un compte réel reste à vérifier.

Les données affichées dépendent des services et de leurs interfaces disponibles. La connexion aux comptes se fait par les outils des fournisseurs ; Nivra ne demande pas les mots de passe.

## Passerelle locale (première version)

La page **Passerelle** démarre un relais sur `127.0.0.1` vers un fournisseur compatible OpenAI. Elle accepte `GET /v1/models`, `POST /v1/chat/completions`, `POST /v1/responses` et `POST /v1/messages` pour les fonctions prises en charge. Les réponses sont transmises au fil de leur réception. Les requêtes doivent utiliser la clé temporaire affichée par Nivra ; la clé du fournisseur et cette clé temporaire restent en mémoire jusqu'à l'arrêt du relais. L'arrêt coupe également les connexions en cours.

Plusieurs fournisseurs peuvent être ajoutés pendant la session. Le premier est le fournisseur par défaut ; un modèle simple sans préfixe lui est envoyé. Pour choisir un fournisseur, utiliser `identifiant/modèle`, par exemple `groq/llama-3.3-70b-versatile`. Les modèles dont le nom contient `/` doivent toujours être préfixés, par exemple `openrouter/openai/gpt-4o`, même lorsqu'un seul fournisseur est actif. Un préfixe inconnu est refusé pour éviter d'envoyer la requête au mauvais fournisseur après un retrait. La liste des modèles combine les catalogues accessibles, qui peuvent être incomplets si un fournisseur ne répond pas.

La liste retournée par `/v1/models` expose les identifiants préfixés pour chaque fournisseur, y compris lorsqu'il est seul. Pour le fournisseur par défaut, les modèles sans barre oblique sont aussi exposés sous leur nom simple.

La liste de préréglages comprend aussi des adresses compatibles Chat Completions comme Together, Fireworks, Cerebras, Hugging Face, NVIDIA NIM, DeepInfra, Kimi, Qwen et MiniMax, ainsi que LM Studio et vLLM locaux. Ces préréglages préremplissent l'adresse et le protocole : ils nécessitent la clé ou le serveur approprié et ne constituent pas une connexion à un abonnement. Le support des fonctions et des catalogues varie selon le service ; ces nouveaux préréglages n'ont pas été vérifiés avec des comptes réels.

Les préréglages API comprennent aussi Nous Research, Nscale, Vultr, Command Code, PackyCode, QwenCloud Token Plan, Tencent Coding Plan, les offres Volcengine, Kilo Gateway, Opper, TokenLab, Modelflare et AI Stupid Level. Ils nécessitent une clé adaptée et n’ont pas été testés avec des comptes réels.

Les préréglages **Cline API** et **ClinePass** utilisent une clé API Cline. Le catalogue affiché est la liste publique des recommandations Cline ; la présence d’un modèle ne garantit pas son accès. Les identifiants comportant une barre oblique doivent conserver le préfixe du fournisseur, par exemple `cline-pass/cline-pass/glm-5.3`. Une fois la passerelle démarrée, « Lire les quotas » affiche les fenêtres renvoyées par Cline pour la clé sélectionnée, lorsqu’elles sont disponibles. La traduction Responses, le catalogue et les quotas sont testés avec des services simulés, sans validation avec une clé réelle. La traduction refuse certains blocs de raisonnement qu’elle ne sait pas conserver.

Le préréglage expérimental **Kiro · AWS Builder ID** permet une connexion par code et conserve les identifiants dans le coffre Windows. Nivra peut demander les modèles et quotas du compte, traduire des conversations texte et images intégrées ainsi que des appels d’outils simples. Les réponses en flux sont transmises après réception complète ; lorsqu’un compte ne communique pas les nombres de tokens, les nombres nécessaires au format Messages sont estimés et signalés par un en-tête. Certaines options et certains modèles ne sont pas pris en charge. Ces parcours sont testés avec des services simulés, pas encore avec un compte Kiro réel.

Le préréglage **Nous Research** propose aussi une connexion expérimentale par code : après autorisation, le compte peut être activé dans la passerelle. Les jetons de renouvellement sont conservés dans le coffre Windows ; le routage est testé avec un fournisseur simulé, mais la connexion et les modèles n’ont pas été vérifiés avec un compte réel. Oublier retire la copie locale sans révoquer l’autorisation chez Nous.

Les offres Alibaba Coding Plan et Token Plan ont chacune un préréglage international et un préréglage Chine ; elles utilisent des clés et des adresses distinctes de l’API à l’usage. Le changement de fournisseur efface la clé saisie dans le formulaire. Ces offres n’ont pas encore été vérifiées avec des clés réelles.

Le préréglage **Qwen · compte avec abonnement** propose une connexion expérimentale par code pour un compte Qwen éligible. Le renouvellement reste dans le coffre Windows et le compte doit être activé après sa connexion. La passerelle utilise actuellement `portal.qwen.ai` ; un compte indiquant une autre adresse est refusé. Des services simulés vérifient l’attente d’autorisation et le routage Responses vers Chat avec le jeton du compte. L’accès aux modèles dépend de l’offre et le parcours complet n’a pas encore été testé avec un compte réel. Oublier retire le jeton local sans révoquer l’autorisation chez Qwen.

Les préréglages **Z.ai GLM Coding Plan** et **BigModel GLM Coding Plan** utilisent les clés et endpoints de leurs régions respectives, distincts du préréglage Z.ai API à l’usage. BigModel propose aussi un préréglage Responses. Pour un fournisseur Coding Plan actif sur une adresse officielle reconnue, **Lire les quotas** affiche les fenêtres et limites que le service renvoie, y compris les outils MCP ; les périodes absentes restent inconnues. La lecture des deux régions a été testée avec des services simulés, pas avec de vraies clés.

Les préréglages **OpenCode Go** et **OpenCode Zen** distinguent l’abonnement de l’offre à l’usage. Pour un fournisseur Go actif à son adresse officielle, **Lire les quotas** affiche les pourcentages utilisés et les dates de renouvellement transmis par OpenCode, sans inventer de plafond en dollars. Les requêtes Responses de quelques modèles Go connus sont envoyées au format Responses natif. Les modèles Go connus utilisant Messages passent par ce format, avec traduction pour les requêtes Responses et Chat courantes ; les autres utilisent Chat Completions. Les requêtes Chat ou Messages vers les modèles nécessitant Responses ne sont pas encore traduites vers ce format, et la liste des protocoles par modèle doit suivre les changements d’OpenCode. Le routage et les quotas restent à vérifier avec une vraie clé et les modèles accessibles au compte.

Le bouton **Ouvrir Codex** lance le CLI Codex installé dans une nouvelle fenêtre avec le modèle et le dossier choisis. Il transmet la configuration uniquement au processus lancé, sans modifier les réglages permanents de Codex ; la clé locale est fournie dans son environnement. Nivra et sa passerelle doivent rester ouvertes pendant la session. Pour un nom de modèle contenant `/`, indique toujours le préfixe d'un fournisseur actif, même s'il n'y en a qu'un. La recherche web intégrée est désactivée pour les fournisseurs traduits. La construction de la commande est testée automatiquement ; l'ouverture interactive depuis l'interface reste à vérifier.

**Ouvrir Claude Code** utilise le même modèle et le même dossier pour ouvrir le CLI Claude Code installé, avec l'adresse et la clé locale transmises à cette session. Les autres identifiants Anthropic présents dans l'environnement ne sont pas transmis à ce processus. La passerelle doit rester active. La construction de la commande est testée ; l'ouverture interactive depuis l'interface reste à vérifier. Les limites de la traduction Messages s'appliquent aux fournisseurs Chat.

Pour les fournisseurs qui n'exposent que Chat Completions, sélectionner **Chat Completions · traduction Responses**. Nivra traduit les échanges Responses courants : texte, images par URL, appels de fonctions, groupes d'outils, résultats d'outils et réponses en streaming. Les conversations stockées, les outils intégrés, les sorties de raisonnement propres à certains fournisseurs et certains types de contenu ne sont pas pris en charge : ces requêtes sont refusées plutôt que transformées silencieusement. Un essai de texte a été effectué avec le client Codex et un fournisseur simulé local, avec la recherche web de Codex désactivée (`web_search = "disabled"`). Cela ne vérifie pas tous les outils ni les fournisseurs réels. Les fonctionnalités réellement disponibles dépendent du fournisseur et de son modèle.

La route Messages traduit les messages et outils courants vers Chat Completions. Dans Claude Code, l'adresse de base est celle affichée sans `/v1` ; la clé à configurer est la clé temporaire de la passerelle. Un échange texte a été testé avec Claude Code en mode minimal et un fournisseur simulé. Les outils intégrés, le raisonnement étendu et la route de comptage de tokens ne sont pas encore pris en charge. Dans les flux traduits, les comptes de tokens peuvent valoir zéro lorsqu'ils ne sont pas fournis à temps par le fournisseur ; ne pas les utiliser pour une facturation.

Le 9 novembre 2026, les clients Codex et Claude Code installés ont chacun réussi un échange texte avec la passerelle et des fournisseurs simulés locaux, en modes Chat et Anthropic natif. Ces essais utilisent des profils temporaires et ne vérifient ni les comptes réels ni l'ouverture interactive depuis les boutons de Nivra.

Le préréglage **Anthropic API** utilise Messages natif : les requêtes Messages et de comptage de tokens sont relayées sans traduction, avec la clé API Anthropic du fournisseur. Les requêtes Responses courantes de Codex peuvent être traduites vers ce fournisseur ; les outils intégrés, les conversations stockées et certains blocs de raisonnement ne sont pas encore pris en charge. Pour les requêtes traduites qui ne précisent pas de limite de sortie, Nivra en fixe une à 8 192 tokens, car l'API Anthropic exige ce paramètre. Cette connexion API est distincte d'un abonnement Claude et des profils Claude Code suivis par Nivra. Les préréglages **Gemini API** et **xAI API** utilisent leurs endpoints compatibles OpenAI ; Gemini API est distinct du compte Antigravity. Ces connexions et leurs modèles n'ont pas encore été vérifiés avec des comptes réels.

La route Chat Completions accepte également le préréglage Anthropic : elle traduit les messages, images, fonctions et réponses courantes, y compris le streaming. Les paramètres non reconnus sont refusés. La traduction a été vérifiée avec un serveur simulé, pas avec une clé Anthropic réelle ; les fonctions propres aux fournisseurs peuvent rester indisponibles.

La passerelle ne garantit pas que chaque fournisseur prenne en charge les routes configurées. Il faut démarrer la passerelle dans Nivra, puis configurer son adresse et sa clé dans l'outil client. Les abonnements et connexions existantes ne sont pas automatiquement transférés ; le compte Google Antigravity peut être ajouté explicitement dans les limites expérimentales décrites ci-dessus.

L'enregistrement d'un fournisseur est facultatif. Les réglages non secrets sont conservés dans les données locales de Nivra et sa clé, si elle existe, est stockée dans le Gestionnaire d'identifiants Windows. La clé est liée à son adresse et à son protocole pour éviter son utilisation avec un autre service. Après un redémarrage ou un arrêt, il faut réactiver les fournisseurs enregistrés ; **Oublier** retire aussi leur clé du coffre. Les fournisseurs non enregistrés restent uniquement en mémoire.

Pour un fournisseur OpenRouter actif utilisant l'adresse officielle, **Lire les limites** affiche à la demande les montants d'utilisation et le plafond de sa clé. Le montant restant concerne le plafond de cette clé et peut différer du solde du compte. Les données non fournies restent indiquées comme indisponibles. Cette lecture a été testée avec un service simulé, pas avec une clé réelle.

Pour un fournisseur DeepSeek API actif utilisant l'adresse officielle, **Lire le solde** affiche les devises et montants renvoyés pour le compte associé à sa clé. Il s'agit du solde API, distinct d'un éventuel compte de chat. La lecture a été testée avec un service simulé, pas avec une clé réelle.

Le bouton **Connecter OpenRouter** ouvre l'autorisation du compte dans le navigateur. OpenRouter crée alors une nouvelle clé pour Nivra ; elle est enregistrée dans le coffre Windows et le fournisseur apparaît dans les fournisseurs enregistrés, à activer ensuite. Le retour local est vérifié par état et PKCE. **Oublier** retire la copie locale, mais ne révoque pas la clé chez OpenRouter : la révoquer dans les réglages OpenRouter si nécessaire. Le parcours complet avec un compte réel reste à vérifier.

## Publier une version

La version de `src-tauri/tauri.conf.json` doit correspondre aux versions de `package.json` et `src-tauri/Cargo.toml`. Après avoir mis à jour ces fichiers et `package-lock.json` / `Cargo.lock`, pousser le code, puis un tag `v` suivi de cette version (par exemple `v0.1.1`). Le workflow GitHub construit l’installateur, sa signature et le fichier `latest.json` pour la mise à jour.

Le dépôt doit disposer des secrets GitHub Actions `TAURI_SIGNING_PRIVATE_KEY` et `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. Conserver une sauvegarde privée de la clé de signature : la perdre empêchera les installations existantes d’accepter les futures mises à jour. Ne jamais la publier dans le dépôt.

Le préréglage **Z.ai GLM API** configure l’adresse Chat Completions documentée par Z.ai et demande une clé API. Il utilise la traduction de la passerelle ; les fonctions propres à Z.ai ne sont pas toutes traduites et le parcours n’a pas été vérifié avec une clé réelle.

Le bouton **Connecter Kimi Code** utilise une autorisation par code, distincte de la clé API. La référence locale est enregistrée dans les fournisseurs et le jeton de renouvellement est stocké dans le coffre Windows ; la passerelle renouvelle l’accès lorsque nécessaire et conserve temporairement en mémoire un accès encore valide. Ce parcours est expérimental et n’a pas été vérifié avec un compte réel. Oublier retire le jeton local sans révoquer l’autorisation chez Kimi.

Pour un compte Kimi Code enregistré, **Lire les quotas** interroge à la demande le service de l’abonnement, sans avoir besoin de démarrer la passerelle. Les détails chiffrés, résumés de périodes et crédits supplémentaires sont affichés séparément lorsqu’ils sont fournis. Kimi peut communiquer des valeurs divergentes entre détail et résumé ; Nivra les restitue sans les fusionner. La lecture a été testée avec des réponses simulées et reste à vérifier avec un compte réel.

Le préréglage **xAI API** propose aussi **Connecter un compte Grok** : ce parcours expérimental utilise l’autorisation du navigateur et la passerelle d’abonnement Grok CLI, distincte de l’API à clé xAI. Le jeton de renouvellement reste dans le coffre Windows. Après connexion, active le compte enregistré pour l’utiliser ; l’accès aux modèles dépend du compte. L’échange et les adresses sont testés localement, mais le parcours complet et les modèles n’ont pas encore été vérifiés avec un compte réel. Oublier retire le jeton local sans révoquer l’autorisation chez xAI.

Le préréglage **GitHub Copilot · compte** propose une connexion expérimentale non officielle par code GitHub. Nivra conserve l’autorisation GitHub dans le coffre Windows, obtient un jeton Copilot temporaire et ne le transmet qu’à une adresse HTTPS autorisée de GitHub Copilot. Un abonnement approprié peut être nécessaire. Les requêtes Responses de certains modèles connus sont relayées en Responses natif ; les autres passent par Chat Completions. Les requêtes Chat et Messages vers les modèles nécessitant Responses ne sont pas encore converties vers ce format et peuvent échouer. Le parcours, le catalogue et les modèles restent à vérifier avec un compte réel. Oublier retire l’autorisation locale sans la révoquer chez GitHub.

Pour chaque compte Copilot enregistré, **Lire les quotas** interroge à la demande le service GitHub non officiel, même si la passerelle est arrêtée. Nivra affiche les quotas premium, chat et complétions quand ils sont communiqués, ainsi que le renouvellement et un éventuel dépassement. Une valeur absente reste inconnue. La lecture et l’analyse ont été vérifiées avec un service simulé ; le résultat dépend du compte et reste à vérifier auprès de GitHub avec un compte réel.
